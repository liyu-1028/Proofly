# 审稿宝系统模块列表

本文档用于指导审稿宝后续按模块开发。模块划分以 MVP 审稿闭环为主线：

```text
创建审稿项目
→ 上传设计稿版本
→ 生成客户审稿链接
→ 客户在线预览并标注意见
→ 设计师处理意见并上传新版
→ 客户确认定稿
→ 系统保存确认记录
```

开发优先级：先完成主流程可用，再完善后台管理、统计、套餐、AI 等扩展能力。

## M01 账号、门店与权限

### 模块目标

建立系统的身份、组织和权限边界。审稿宝第一版即使只做单店部署，也要保留 `store_id`，便于后续扩展到多门店或 SaaS 平台。

### 核心功能

- 门店管理：创建门店、编辑门店名称、联系方式、状态。
- 员工管理：创建员工账号、编辑资料、启用、停用。
- 登录认证：支持门店后台用户登录、退出、获取当前用户信息。
- 角色管理：至少区分门店老板、设计师、管理员。
- 权限边界：后台接口需要登录；客户审稿链接接口使用访问令牌，不要求客户注册登录。

### 主要数据

| 数据对象 | 说明 |
| --- | --- |
| `store` | 门店信息 |
| `user` | 后台用户和员工账号 |
| `role` | 角色定义 |
| `user_role` | 用户与角色关系 |

### 后端建议

- 包名建议：`store`、`user`、`auth`、`permission`。
- 所有后台业务查询默认按 `store_id` 隔离。
- MVP 可先使用简单 RBAC，不需要过早实现复杂菜单权限。
- 密码必须加密存储，不保存明文密码。

### 前端页面

- 登录页。
- 当前用户信息与退出入口。
- 员工列表、员工编辑页。
- 门店基础设置页。

### 验收标准

- 门店员工可以登录后台。
- 设计师只能操作自己门店下的数据。
- 客户审稿链接无需后台账号即可访问指定审稿内容。

## M02 审稿项目

### 模块目标

承载一次客户审稿任务，是设计稿版本、标注、确认记录的业务主容器。

### 核心功能

- 创建审稿项目。
- 编辑项目名称、客户信息、负责人、备注。
- 查看项目列表和详情。
- 按门店、负责人、状态、客户关键字筛选。
- 项目归档和恢复。
- 项目状态流转。

### 项目状态建议

| 状态 | 含义 |
| --- | --- |
| `draft` | 草稿，尚未发送给客户 |
| `waiting_feedback` | 等待客户反馈 |
| `change_requested` | 客户已提交修改意见 |
| `waiting_confirm` | 等待客户确认定稿 |
| `confirmed` | 客户已确认定稿 |
| `archived` | 已归档 |

### 主要数据

| 数据对象 | 说明 |
| --- | --- |
| `project` | 审稿项目主表 |
| `project_member` | 项目协作者，MVP 可选 |
| `project_status_log` | 项目状态变更日志 |

### 后端建议

- 包名建议：`project`。
- 项目创建时必须绑定 `store_id` 和负责人。
- 项目状态由业务动作驱动，避免前端随意改状态。
- 归档不等于删除，归档项目仍保留版本、标注和确认记录。

### 前端页面

- 项目列表。
- 创建项目弹窗或页面。
- 项目详情页。
- 项目状态筛选和搜索。

### 验收标准

- 设计师能创建项目并在列表中看到。
- 项目详情能展示客户信息、当前状态、当前版本、标注数量和确认状态。
- 已确认项目不能被随意改回未确认状态。

## M03 设计稿版本

### 模块目标

保证每次上传都是独立版本，历史版本不可覆盖。客户确认必须绑定到具体版本。

### 核心功能

- 为项目上传新版本。
- 查看版本列表。
- 设置当前展示版本。
- 查看历史版本。
- 记录版本说明、上传人、上传时间、文件信息。
- 标记某个版本已被客户确认。

### 版本规则

- 版本号按项目内递增，例如 `V1`、`V2`、`V3`。
- 上传新版不删除旧版文件和旧版标注。
- 标注评论必须绑定具体版本。
- 确认记录必须绑定具体版本。
- 项目已确认后，默认不允许继续上传新版本；如业务需要返工，应另起项目或增加明确的返工流程。

### 主要数据

| 数据对象 | 说明 |
| --- | --- |
| `project_version` | 设计稿版本 |
| `file_object` | 文件元数据 |

### 后端建议

- 包名建议：`version`。
- 上传版本需要同时写入 `project_version` 和 `file_object`，Service 层处理事务边界。
- 文件已上传但数据库写入失败时，需要有清理或重试策略。
- 当前版本可由 `project.current_version_id` 保存，也可通过版本状态计算，MVP 建议显式保存。

### 前端页面

- 项目详情中的版本列表。
- 版本上传入口。
- 版本切换器。
- 版本说明展示。

### 验收标准

- 同一项目能上传多个版本。
- 切换历史版本时，预览、标注、确认状态都随版本变化。
- 已确认版本能在界面上明确标识。

## M04 文件上传、存储与预览

### 模块目标

负责设计稿文件上传、对象存储、元数据管理和在线预览能力。

### 核心功能

- 上传设计稿原文件。
- 存储到 MinIO。
- 保存文件元数据到 MySQL。
- 生成或保存预览地址。
- 提供文件下载、预览访问能力。
- 限制文件大小和文件类型。

### MVP 文件类型建议

| 类型 | MVP 处理方式 |
| --- | --- |
| 图片：JPG、JPEG、PNG、WEBP | 直接在线预览 |
| PDF | 首版可直接嵌入浏览器预览，后续可转图片 |
| AI、PSD、CDR 等源文件 | 首版可先作为附件保存，要求设计师同时上传预览图 |

### 主要数据

| 数据对象 | 说明 |
| --- | --- |
| `file_object` | 文件对象元数据 |
| `file_preview` | 预览图或派生文件，MVP 可选 |

### MinIO 路径建议

```text
stores/{storeId}/projects/{projectId}/versions/{versionId}/{fileId}-{filename}
```

### 后端建议

- 包名建议：`file`、`storage`。
- MySQL 保存对象 key、原始文件名、扩展名、MIME、大小、校验值、上传人。
- 不把 MinIO 内部地址直接暴露给客户，优先由后端生成受控访问地址。
- 删除文件需要遵守版本和确认留痕规则，默认不允许删除已确认版本关联文件。

### 前端页面

- 文件上传组件。
- 预览组件。
- 文件错误提示。
- 上传进度和失败重试。

### 验收标准

- 设计师可以上传图片并在线预览。
- 文件元数据能和版本正确关联。
- 客户通过审稿链接只能查看被授权项目的文件。

## M05 客户审稿链接

### 模块目标

让客户无需注册登录即可打开指定项目的审稿页面，同时保证链接权限可控、可追踪。

### 核心功能

- 为项目生成客户审稿链接。
- 支持复制链接。
- 支持访问令牌校验。
- 可选支持过期时间、访问次数限制、重新生成链接。
- 记录访问来源、IP、User-Agent 等信息。

### 主要数据

| 数据对象 | 说明 |
| --- | --- |
| `review_link` | 审稿链接和访问令牌 |
| `review_access_log` | 客户访问日志 |

### 后端建议

- 包名建议：`reviewlink` 或 `share`。
- 客户端公开接口和后台接口分开，例如 `/api/admin/**` 与 `/api/public/reviews/**`。
- 访问令牌只授权访问单个项目或单个审稿任务。
- 令牌不要直接使用连续 ID，避免被枚举。

### 前端页面

- 项目详情中的复制链接按钮。
- 客户审稿公开页。
- 链接失效页。

### 验收标准

- 设计师能生成并复制审稿链接。
- 客户打开链接后只能访问对应项目。
- 失效或错误链接有明确提示。

## M06 在线标注评论

### 模块目标

让客户在设计稿指定位置提交修改意见，让设计师能按版本集中查看和处理。

### 核心功能

- 客户在预览图上点击或框选位置。
- 客户填写修改意见。
- 设计师查看标注列表和标注位置。
- 设计师回复、标记已处理或忽略。
- 标注按版本隔离。

### 标注类型建议

| 类型 | 含义 |
| --- | --- |
| `point` | 点位标注 |
| `rect` | 矩形区域标注 |
| `text` | 纯文字意见，MVP 可选 |

### 标注状态建议

| 状态 | 含义 |
| --- | --- |
| `open` | 待处理 |
| `resolved` | 已处理 |
| `ignored` | 已忽略 |

### 主要数据

| 数据对象 | 说明 |
| --- | --- |
| `annotation` | 标注主表 |
| `annotation_comment` | 标注回复，MVP 可选 |

### 后端建议

- 包名建议：`annotation`。
- 坐标建议保存为相对比例，而不是像素绝对值，例如 `x_ratio`、`y_ratio`、`width_ratio`、`height_ratio`。
- 标注必须绑定 `store_id`、`project_id`、`version_id`。
- 客户提交标注后，项目状态可流转为 `change_requested`。

### 前端页面

- 客户审稿页标注工具。
- 设计师项目详情标注列表。
- 标注定位、筛选、状态切换。

### 验收标准

- 客户能在设计稿上添加位置标注和文字意见。
- 设计师能看到标注位置和内容。
- 上传新版本后，旧版本标注仍能在旧版本中查看。

## M07 客户确认定稿

### 模块目标

让客户对指定版本执行“确认定稿”，并形成后续生产和争议处理依据。

### 核心功能

- 客户点击确认定稿。
- 确认前展示项目名、版本号、确认提示。
- 记录确认人信息。
- 记录确认时间、IP、User-Agent、访问令牌。
- 确认后更新项目和版本状态。
- 已确认记录不可随意删除。

### 确认规则

- 确认动作必须绑定具体 `project_version`。
- 一个项目默认只有一个最终确认版本。
- 确认后项目状态变为 `confirmed`。
- 已确认版本的文件、版本、确认记录默认不可物理删除。

### 主要数据

| 数据对象 | 说明 |
| --- | --- |
| `confirmation_record` | 客户确认记录 |

### 后端建议

- 包名建议：`confirmation`。
- 确认接口必须幂等：重复点击不应产生多条有效最终确认记录。
- 关键字段建议包含：`store_id`、`project_id`、`version_id`、`customer_name`、`customer_contact`、`confirmed_at`、`ip`、`user_agent`、`review_token_id`。
- 如后续需要撤销确认，应新增“作废记录”，不要直接删除原确认记录。

### 前端页面

- 客户审稿页确认按钮。
- 确认弹窗。
- 确认成功页或确认状态提示。
- 项目详情确认记录区。

### 验收标准

- 客户能确认当前版本。
- 设计师在后台能看到确认版本、确认时间和确认人信息。
- 重复确认不会破坏已有确认记录。

## M08 审稿行为与确认记录

### 模块目标

保存关键审稿行为，为项目追踪、责任确认和争议处理提供依据。

### 核心功能

- 记录项目创建、上传版本、提交标注、处理标注、客户访问、客户确认等事件。
- 展示项目时间线。
- 查询确认记录。
- 后续支持导出确认单或 PDF。

### 主要数据

| 数据对象 | 说明 |
| --- | --- |
| `audit_log` | 通用操作日志 |
| `review_access_log` | 客户访问日志 |
| `confirmation_record` | 确认记录 |

### 后端建议

- 包名建议：`audit`、`record`。
- 关键业务动作在 Service 层统一写日志。
- 操作日志可先做轻量表结构，避免过度设计。
- 确认记录和审计日志不依赖 Redis，必须落库。

### 前端页面

- 项目详情时间线。
- 确认记录详情。
- 后续确认单导出入口。

### 验收标准

- 项目详情能看到关键行为时间线。
- 确认记录能独立查询。
- 日志可以说明“谁在什么时间对哪个版本做了什么”。

## M09 后台工作台与状态看板

### 模块目标

帮助门店老板和设计师快速了解项目进度、待处理事项和近期审稿活动。

### 核心功能

- 项目状态统计。
- 我的待处理项目。
- 最近客户反馈。
- 最近确认记录。
- 按设计师、状态、时间筛选。

### 后端建议

- 包名建议：`dashboard`。
- 首版统计可直接查询 MySQL。
- 数据量增大后再考虑 Redis 缓存或异步汇总。

### 前端页面

- 后台首页。
- 状态统计卡片。
- 待办列表。
- 近期动态列表。

### 验收标准

- 设计师登录后能看到自己负责的待处理项目。
- 门店老板能看到门店整体审稿状态。

## M10 通知与提醒

### 模块目标

在客户反馈、设计师处理、客户确认等节点提供提醒能力，减少人工追问。

### 核心功能

- 复制审稿链接时生成提醒文案。
- 客户提交标注后提醒设计师。
- 设计师上传新版后提醒客户。
- 客户确认后提醒项目负责人。
- 后续扩展短信、邮件、微信公众号、企业微信等渠道。

### 后端建议

- 包名建议：`notification`。
- MVP 可先实现站内通知和提醒文案生成。
- 第三方通知渠道通过适配器封装，避免侵入业务 Service。

### 前端页面

- 通知列表。
- 未读提示。
- 项目详情中的提醒入口。

### 验收标准

- 关键动作能生成可查看的通知记录。
- 后续接入真实通知渠道时，不需要重写主业务流程。

## M11 系统配置与基础数据

### 模块目标

集中管理系统运行参数和可配置业务规则。

### 核心功能

- 文件大小限制。
- 允许上传的文件类型。
- 审稿链接默认有效期。
- 门店基础信息。
- 项目状态、标注状态等字典配置。

### 后端建议

- 包名建议：`config`、`dict`。
- 环境级配置放在 `application-*.yml` 和环境变量中。
- 业务级配置可落库。
- MVP 阶段不要做过于复杂的配置中心。

### 前端页面

- 系统设置页。
- 文件上传设置。
- 门店资料设置。

### 验收标准

- 管理员可以调整常用业务参数。
- 敏感配置仍通过环境变量管理，不写入前端。

## M12 部署、运维与开放接口

### 模块目标

支撑本地开发、测试、部署、健康检查和接口协作。

### 核心功能

- Docker Compose 开发环境。
- MySQL、Redis、MinIO 配置。
- 健康检查接口。
- OpenAPI 文档。
- 环境变量示例。

### 后端建议

## M13 套餐、用量与账单

### 模块目标

为后续 SaaS 化和商业化预留。MVP 不强制实现，但核心表保留 `store_id` 可降低后续改造成本。

### 可能功能

- 套餐管理。
- 门店订阅状态。
- 项目数、存储空间、员工数用量统计。
- 账单记录。
- 到期提醒。

### 后端建议

- 包名建议：`billing`、`subscription`。
- 不要在 MVP 主流程里写死套餐限制。
- 如果需要限制用量，优先通过独立策略服务判断。

### 验收标准

- MVP 阶段无需完成。
- 数据模型和业务代码不阻碍后续按门店统计用量。

## M14 AI 辅助能力

### 模块目标

在审稿主流程稳定后，增加智能辅助能力，提高设计师整理意见和回复客户的效率。

### 可能功能

- 自动总结客户标注意见。
- 根据历史修改意见生成待办清单。
- 辅助生成客户沟通文案。
- 智能审稿建议。
- 门店知识库问答。

### 后端建议

- 包名建议：`ai`、`assistant`、`knowledge`。
- AI 模块必须独立于审稿主流程，不能影响上传、标注、确认的可靠性。
- 可后续按需要引入 LangChain4j 或 Spring AI。
- AI 生成内容必须保留人工确认入口。

### 验收标准

- MVP 阶段无需完成。
- 后续接入时不改变核心确认记录和版本规则。

## 推荐开发顺序

## 核心 API 分组

接口文档按模块拆分维护。文件名使用 `docs/api-mXX-module-name.md` 格式，每完成一个新模块功能时创建或更新该模块接口文档。

当前已建立的模块接口文档：

| 模块 | 接口文档 |
| --- | --- |
| M01 账号、门店与权限 | `docs/api-m01-account-store-permission.md` |
| M12 部署、运维与开放接口 | `docs/api-m12-deployment-ops-openapi.md` |

| API 分组 | 说明 |
| --- | --- |
| `/api/auth/**` | 登录、退出、当前用户 |
| `/api/admin/stores/**` | 门店管理 |
| `/api/admin/users/**` | 员工管理 |
| `/api/admin/projects/**` | 审稿项目 |
| `/api/admin/projects/{projectId}/versions/**` | 设计稿版本 |
| `/api/admin/files/**` | 后台文件上传与管理 |
| `/api/admin/review-links/**` | 审稿链接管理 |
| `/api/admin/annotations/**` | 后台标注处理 |
| `/api/admin/confirmations/**` | 确认记录查询 |
| `/api/admin/dashboard/**` | 工作台统计 |
| `/api/public/reviews/**` | 客户公开审稿访问 |
| `/api/public/reviews/{token}/annotations/**` | 客户提交标注 |
| `/api/public/reviews/{token}/confirmations/**` | 客户确认定稿 |

接口设计原则：

- 后台接口需要登录态和门店权限。
- 公开审稿接口只接受审稿令牌授权。
- 请求和响应使用 DTO/VO，不直接暴露数据库实体。
- 涉及上传、确认、状态变更的接口必须在 Service 层处理事务和日志。

## MVP 完成定义

MVP 至少需要满足以下完整路径：

1. 门店员工登录后台。
2. 设计师创建审稿项目。
3. 设计师上传设计稿，系统生成版本。
4. 系统生成客户审稿链接。
5. 客户打开链接在线查看设计稿。
6. 客户在设计稿上提交标注意见。
7. 设计师在后台查看标注并上传新版本。
8. 客户再次打开链接查看新版。
9. 客户点击确认定稿。
10. 系统保存确认记录，并在后台展示确认版本、确认时间、确认人和关键访问来源。

只要这个闭环稳定可用，后续模块都可以围绕它迭代增强。
